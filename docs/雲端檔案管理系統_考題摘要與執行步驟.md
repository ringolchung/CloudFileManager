# 雲端檔案管理系統 — 考題摘要與建議執行步驟

## 一、考題摘要

**角色**：系統分析師（SA）。依客戶訪談紀錄做領域建模，並實作核心邏輯。

**重點**：考的是「物件導向分析 + 設計模式 + 架構思維」，不需要 GUI（做 Web UI 為加分）。**允許使用 AI 工具**。

**繳交**：GitHub 連結 + 設計與實作概念說明。

### 需求整理（從訪談萃取）

| 項目 | 內容 |
|---|---|
| 檔案共同屬性 | 檔名、大小（KB）、建立時間 |
| Word 檔 | 頁數 |
| 圖片 | 解析度（寬、高） |
| 純文字檔 | 編碼（UTF-8、ASCII…） |
| 目錄 | 有名稱；可包含檔案與子目錄；**巢狀深度無限制** |
| 限制 | 檔案**必須**屬於某個目錄，不能獨立存在 |

> 隱含的設計訊號：「目錄可包含目錄與檔案、可無限巢狀」＝ **Composite Pattern（組合模式）**

### 三項交付物

1. **UML Class Diagram**：呈現繼承、關聯／聚合（組合）關係
2. **ER Model（Schema 設計）**：資料庫表格與關聯
3. **程式實作**：C# / Java / Python / TypeScript 皆可，Console 輸出驗證

### 功能要求

| 層級 | 功能 | 說明 |
|---|---|---|
| 必做 1 | 目錄結構呈現 | 依範例建立物件樹，印出樹狀結構與各檔案詳細資訊 |
| 必做 2-a | 遞迴計算總容量 | 任一目錄的總大小（含所有子層） |
| 必做 2-b | 副檔名搜尋 | 輸入 `.docx` 列出所有符合檔案的**完整路徑** |
| 必做 2-c | XML 輸出 | 依指定格式輸出（名稱中的 `.` 轉 `_`，如 `需求規格書_docx`） |
| 必做 3 | 遍歷紀錄 | 計算與搜尋時印出 `Visiting: Root -> Project_Docs -> 需求規格書.docx ...` |
| 加分 4 | 排序 | 依名稱／大小／副檔名，升冪／降冪 |
| 加分 4 | 編輯 | 刪除、複製／貼上 |
| 加分 4 | 標籤 | Urgent(紅)、Work(藍)、Personal(綠)，支援多重標籤 |
| 加分 4 | Undo / Redo | 操作的復原與重做 |

### 範例資料結構（需照此建立）

```
根目錄 (Root)
├── 專案文件 (Project_Docs) [目錄]
│   ├── 需求規格書.docx [Word] (頁數: 15, 大小: 500KB)
│   └── 系統架構圖.png [圖片] (解析度: 1920x1080, 大小: 2MB)
├── 個人筆記 (Personal_Notes) [目錄]
│   ├── 待辦清單.txt [純文字] (編碼: UTF-8, 大小: 1KB)
│   └── 2025備份 (Archive_2025) [子目錄]
│       └── 舊會議記錄.docx [Word] (頁數: 5, 大小: 200KB)
└── README.txt [純文字] (編碼: ASCII, 大小: 500B)
```

## 二、建議執行步驟

### Step 0：先選語言與環境（10 分鐘）
- 選你最熟的語言。建議 **Java / C# / TypeScript / Python** 其一。
- 若要加分做 Undo/Redo，靜態型別語言（Java、C#、TS）在展示設計模式時較清楚。
- 建立 GitHub repo，開好 `README.md`、`docs/`、`src/`、`tests/` 目錄。

### Step 1：領域分析與 UML 類別圖（約 1 小時）
建議的類別設計：

- `FileSystemNode`（抽象）：`name`, `size`, `createdAt`, `parent`, `tags`
- `File`（抽象，繼承 Node）：`extension`
  - `WordFile`：`pageCount`
  - `ImageFile`：`width`, `height`
  - `TextFile`：`encoding`
- `Directory`（繼承 Node）：`children: List<FileSystemNode>`（**組合 Composition**，1 對 0..*）
- `Tag`（Enum 或類別）：Urgent / Work / Personal，與 Node 為多對多

**畫圖重點**：
- 繼承用空心三角箭頭；Directory → Node 用**實心菱形**（組合：目錄刪除，子節點一併消失）
- 「檔案必須屬於目錄」：`parent` 為必填（多重性 `1`），根目錄例外
- 用 Mermaid 或 PlantUML 畫，可直接放進 README 由 GitHub 渲染

### Step 2：ER Model / Schema 設計（約 45 分鐘）
建議資料表：

- `nodes`：`id`, `parent_id`(FK 自我參照), `name`, `type`(DIR/WORD/IMAGE/TEXT), `size_kb`, `created_at`
- 子類型資料，二擇一並在文件中說明取捨：
  - **Class Table Inheritance**：`word_files(node_id, page_count)`、`image_files(node_id, width, height)`、`text_files(node_id, encoding)`
  - **Single Table**：全放 `nodes`，不適用欄位為 NULL（簡單但有空值）
- `tags`：`id`, `name`, `color`
- `node_tags`：`node_id`, `tag_id`（多對多關聯表）

**要點**：`parent_id` 自我參照表達無限層級；根目錄 `parent_id = NULL`；非根節點 `parent_id NOT NULL` 對應「檔案不可孤立」；(parent_id, name) 加唯一約束避免同目錄重名。可補充遞迴查詢（Recursive CTE）取得子樹。

### Step 3：核心實作（Must-have，約 2–3 小時）
1. **模型類別**：照 UML 實作，`Directory.getSize()` 遞迴加總（這是 Composite 的標準示範）
2. **建立範例資料**：寫一個 `SampleDataBuilder` 依圖建立物件樹
3. **樹狀列印**：遞迴 + 前綴字串處理 `├──`、└──`、`│`
4. **計算總容量**：遞迴，過程印 `Visiting: ...`
5. **副檔名搜尋**：遞迴、累積路徑，輸出完整路徑，過程印 `Visiting: ...`
6. **XML 輸出**：注意名稱轉換規則（`.` → `_`、括號英文名的取捨，如 `Archive_2025`、`Project_Docs`），逐字對照範例格式
7. **單位處理**：範例混用 KB / MB / B（500B、2MB），建議內部統一用 **Byte** 儲存，輸出時格式化，避免 1MB = 1000 或 1024 的歧義（在文件註明你採用哪一種）

> **建議用 Visitor Pattern** 實作「計算大小、搜尋、XML 輸出、列印」：新增操作不用改節點類別，且能共用統一的遍歷／Log 機制，展現架構思維。

### Step 4：Bonus 功能（依時間優先順序）
| 優先 | 功能 | 建議模式／做法 |
|---|---|---|
| 1 | 排序 | **Strategy Pattern**（Comparator：名稱／大小／副檔名 + 升降冪） |
| 2 | 標籤 | Node 持有 `Set<Tag>`，列印時顯示並用 ANSI 色碼著色 |
| 3 | 刪除／複製貼上 | 複製需 **深拷貝**（Prototype / clone）；貼上需處理重名 |
| 4 | Undo / Redo | **Command Pattern** + 兩個 Stack（undo / redo），刪除、貼上、貼標籤皆做成 Command |

做不完時，寧可少做但做好，並在 README 說明「未完成項目與原因／設計構想」。

### Step 5：驗證與測試（約 1 小時）
- 寫單元測試：總容量（範例預期：500KB + 2MB + 1KB + 200KB + 500B）、搜尋 `.docx` 應得 2 筆、XML 輸出與範例比對
- 一個 `Main` 依序展示所有功能，Console 輸出可直接截圖或貼進 README

### Step 6：文件與繳交（約 1 小時）
README 建議結構：
1. 專案簡介與執行方式（一行指令即可跑）
2. 需求分析與假設（例如單位換算、根目錄定義）
3. UML 類別圖、ER 圖
4. 使用的設計模式與**為何選用**（Composite / Visitor / Strategy / Command）
5. 功能展示（Console 輸出截圖或文字）
6. AI 工具使用說明（誠實說明哪裡用 AI、你如何驗證與調整）
7. 未來改進方向

## 三、評分重點與注意事項

- **加分關鍵**：能說明「為什麼」這樣設計（Composite 對應無限巢狀、Visitor 對應多種操作），比單純程式能跑更重要
- **容易失分的地方**：
  - XML 格式沒完全對齊範例（命名轉換、縮排）
  - 容量單位換算錯誤（KB / MB / B 混用）
  - 沒有印出遍歷 Log，或搜尋結果沒顯示完整路徑
  - 檔案可脫離目錄存在（違反業務規則）
- **AI 工具**：題目明確允許，但要能解釋每一段程式；面試時可能被追問設計取捨
- **建議時間分配**：分析與圖 25%、核心實作 40%、Bonus 15%、測試 10%、文件 10%
